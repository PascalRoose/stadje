# Phase 0 Research: Daily City Puzzle

All tech-stack choices (framework, hosting, database, ORM, test runner, linter, language, package
manager) were already decided in the constitution and ADRs 0001–0012 before this feature's spec
even existed — there is nothing left to research there. What remains are implementation-level
"how" decisions specific to this feature, each small enough to be an ordinary code decision rather
than a new ADR (constitution's Development Workflow ADR rule: "costly to reverse" architecture,
not routine implementation choices).

## Decision: Server-side-only hint computation

**Decision**: Hints (province match, population direction/tier, distance/direction) are computed
by an API route (`app/api/puzzle/guess`) that has access to the day's real answer; the client only
ever sends a candidate city id and receives back the computed hint, never the answer's raw data
needed to compute it.

**Rationale**: Computing a hint requires the answer's province/population/coordinates. If that data
reached the client (e.g., to compute hints client-side), it would be visible in browser dev tools
before the player finishes guessing — trivially spoiling every puzzle. Server-side computation is
the only way to satisfy spec FR-006/FR-007 without leaking FR-010's reveal early.

**Alternatives considered**: Client-side hint computation with the day's answer fetched once and
kept in memory — rejected outright, defeats the game. Encrypting/obfuscating the answer client-side
— rejected as unnecessary complexity (Principle V) when a server round-trip per guess is simple,
already required for network play, and has no meaningful latency concern at this scale.

## Decision: No server-side per-player guess state

**Decision**: The guess API is stateless per request — it takes `(date, cityId)`, looks up that
date's answer, and returns hints. It does not track how many guesses a given player has made, does
not reject a player's own duplicate guesses, and has no player identifier at all.

**Rationale**: Constitution Principle VI forbids a server-side player profile. Guess-count limits
(FR-005) and duplicate-guess rejection (FR-004) are therefore enforced client-side against the
player's own `localStorage` history — the same trust boundary as the rest of the client-held game
state. This is consistent with the game being casual, not adversarial: a player who tampers with
their own client only spoils the game for themselves.

**Alternatives considered**: A short-lived server session/cookie to track guesses server-side —
rejected, reintroduces exactly the server-side player state Principle VI prohibits, for a rule
(max 6 guesses) that has no security stakes.

## Decision: Day→city cycle assignment generated by an in-repo seeded shuffle, committed as static data

**Decision**: A small, dependency-free deterministic PRNG (a single ~10-line function, e.g. a
`mulberry32`-style generator) seeded by a fixed value performs a Fisher-Yates shuffle over city ids
once per cycle. The *resulting* per-date assignment is generated by a script and committed to the
repo as a static data file (e.g. `data/puzzle-cycle.json`), imported only by server-side code
(`app/api/*` route handlers) — never by client components, so it isn't shipped in the client
bundle even though it lives in source control.

**Rationale**: Implements ADR 0011 directly, including its explicit acceptance of the
public-source predictability tradeoff (ADR 0011) — the project owner decided that's fine for a
hobby project. Storing the assignment as committed static data (rather than a Neon table) removes
a database dependency and a round trip from the hottest path (looking up "today's city"),
reinforcing Principle V. Keeping the import server-side-only still ensures a casual player can't
see today's (or a future) answer just by opening the page or its network tab — the concern this
addresses is different from, and unaffected by, the predictability tradeoff above.

**Alternatives considered**: A well-known seeded-random npm package (`seedrandom`, `pure-rand`) —
rejected as an unnecessary dependency for ~10 lines of code. Storing the generated assignment in
Neon instead of the repo — rejected as unneeded complexity now that the predictability tradeoff is
explicitly accepted; Neon is reserved for `world_stats_daily`, the one table that's genuinely
mutable and shared in real time (see below).

## Decision: Haversine distance + initial-bearing formula for direction/distance hints

**Decision**: Implement the haversine great-circle distance formula and the initial-bearing formula
directly (using the `latitude`/`longitude` fields already in `data/cities.json`), rounding distance to
whole kilometers (spec FR-006) and quantizing bearing to 8 compass directions (N/NE/E/SE/S/SW/W/NW)
to match the mockup's single-arrow hint presentation.

**Rationale**: Both formulas are short, well-known, and dependency-free; Principle V disfavors
adding a geospatial library for two formulas this small.

**Alternatives considered**: A geospatial npm package (`geolib`, `turf`) — rejected as
disproportionate for two formulas. Great-circle vs. a flat-Earth approximation — haversine chosen
for correctness at Dutch distances (a flat approximation's error is negligible at this scale but
haversine is no more complex to implement).

## Decision: Client-side, in-memory substring/prefix search over the bundled dataset for autocomplete

**Decision**: The full city dataset (178 entries today) ships as static data to the client; the
guess-input autocomplete (FR-003) filters it in-browser by substring match against display name and
aliases, case- and diacritic-insensitive.

**Rationale**: The dataset is small enough that a client-side filter is instant and needs no
network round-trip per keystroke, and no separate search service. Shipping the full dataset
client-side is safe — every city is guessable (spec's resolved FR-003), so there's no answer to
leak by exposing the list itself, only by exposing which one is *today's* answer (kept server-side,
see above).

**Alternatives considered**: A server-side search API — rejected as unnecessary latency and
complexity for a dataset this size (Principle V). This should be revisited if/when the dataset
grows toward the ~612-city target noted in the spec's Assumptions, but that growth is out of scope
here.

## Decision: Single namespaced `localStorage` blob, versioned

**Decision**: All client-held state (per-date guess histories, derived stats/streak, consent
choice, settings) lives under one JSON blob in `localStorage`, with a `schemaVersion` field to allow
future migrations.

**Rationale**: Keeps client-storage code in one place (`lib/local-storage.ts`) and makes "read
everything, migrate if the version is old, write everything back" a single simple code path —
fits Principle V better than juggling many separate keys.

**Alternatives considered**: Separate `localStorage` keys per concern (guesses, stats, consent,
settings) — rejected as marginally more granular but with no real benefit at this data volume, and
more surface area for partial-write inconsistency.

## Decision: World-stats storage is pure aggregate counters, no per-completion rows

**Decision**: `POST /api/world-stats` (only called after consent, FR-017/FR-024) increments a
per-date row's counters directly (players count, correct count, guesses sum, a per-city first-guess
tally, and a running minimum for fastest solve) rather than inserting one row per completed puzzle.

**Rationale**: Satisfies FR-024's required outputs (player count, % correct, average guesses, most
common first guess, fastest solve) while storing the least amount of data possible — an aggregate
counter carries no per-player trace at all, reinforcing Principle VI even for the one piece of
gameplay data that does reach the server.

**Alternatives considered**: Storing one row per completed, opted-in puzzle and aggregating on read
— rejected as retaining more (still anonymous, but individually-distinguishable) data than the
feature needs, and adds read-time aggregation cost for no benefit.

## Decision: Server-resolved "today," never trusting client-supplied dates for the live puzzle

**Decision**: Any endpoint resolving "today's puzzle" computes the current Europe/Amsterdam
calendar date on the server (via `Intl.DateTimeFormat` with `timeZone: 'Europe/Amsterdam'`, no
dependency needed) rather than accepting a client-supplied "today." A client may request a specific
past date (for archive replay, spec FR-016) but never a future one.

**Rationale**: Directly implements constitution Principle I's "identical for every player,
Europe/Amsterdam boundary, regardless of device timezone" — a device with a wrong or manipulated
clock must not be able to see tomorrow's puzzle early or get "yesterday" past the shared boundary.

**Alternatives considered**: Trusting client-supplied dates — rejected, breaks Principle I's
determinism/fairness guarantee outright.

## Decision: Next.js `next/image` against existing Wikimedia Commons URLs, no re-hosting

**Decision**: City photos are rendered via `next/image`, sourced from `data/cities.json`'s existing
`image.url` values (Wikimedia Commons) — but only ever fetched server-side, through this app's own
`GET /api/puzzle/image` proxy (contracts/api.md), never linked to directly from the client before a
puzzle is over. Next.js's remote image patterns are configured for `upload.wikimedia.org` so the
proxy route itself can fetch from it, but the client-facing `imageUrl` is always our own path.

**Rationale**: Avoids adding image *storage*/CDN infrastructure (Principle V) when the existing
URLs are already stable, licensed, and credited per the constitution's Data & Content Standards —
but a same-session correction found that exposing the raw origin URL directly to the client is a
real spoiler bug, not just a simplicity tradeoff: Wikimedia Commons filenames routinely embed the
place name (e.g. `Veendam_105.JPG`), so shipping that URL (or the Commons file-page URL used for
attribution's `source` link) to the client would leak the answer before any guess. The proxy keeps
"no re-hosting" true in the storage sense (nothing is persisted, each request streams through) while
closing that leak; `imageCredit.source` is likewise withheld from `GET /api/puzzle` and only
included in the win/loss reveal payload, once it's no longer a spoiler.

**Alternatives considered**: Re-hosting images in Vercel/Neon or a blob store — rejected as
unnecessary infrastructure for a hobby project with no evidence the source URLs are unreliable.
Linking directly to the origin URL (the original plan) — rejected once testing showed it leaks the
answer via the filename/file-page URL.
